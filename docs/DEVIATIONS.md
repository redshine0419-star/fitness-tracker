### 17. Header — 메가메뉴 hover 유지 로직을 `.navItem`에서 `.header`로 이동 (버그 수정, 서브페이지 작업 이후)

- **무엇을**: 메가메뉴 폭 버그(DEVIATIONS 없음, 이전 커밋에서 `.navItem`의 `position:relative` 제거로 수정)를 고치면서, `.panel`이 `.header`(position:sticky) 기준으로 전체 폭에 펼쳐지게 됐다. 그런데 열림/닫힘을 담당하는 `onMouseLeave={closeMenu}`는 여전히 작은 `<li>`(`.navItem`)에 붙어 있어서, 마우스가 링크에서 패널로 내려가는 도중 `<li>`의 작은 hover 영역과 `.header` 바닥에서 시작하는 패널 사이의 빈 공간(같은 `.header` 안이지만 `<li>`도 `.panel`도 아닌 배경 영역)을 지날 때 `<li>`의 `mouseleave`가 먼저 발동해, 패널에 마우스가 닿기도 전에 메뉴가 닫혀버리는 실제 버그가 있었다(사용자 리포트로 발견, Playwright로 단계별 마우스 이동을 재현해 정확한 좌표까지 확인).
- **왜**: `mouseleave`는 DOM 상 자손 요소(`.panel`)로 들어가는 동안에는 발동하지 않지만, 그 경로 중간에 자손도 아니고 자기 자신도 아닌 제3의 영역(`.header`의 나머지 배경)을 지나가면 즉시 발동한다. `.panel`이 `.header`를 기준으로 위치하면서 `.header`의 바닥(패널 시작점)과 `<li>`의 실제 hover 영역(그보다 훨씬 작음) 사이에 이 "죽은 공간"이 생겼다. 이 죽은 공간을 없애려면 hover-leave 판정 기준을 패널과 맞닿아 있는(간격이 전혀 없는) 요소로 옮겨야 하는데, `.header` 자체가 정확히 그 조건을 만족한다(`.panel`의 `top:100%`가 `.header` 바로 밑에서 시작해 완전히 맞닿음).
- **대안**: `<li>`에 padding-bottom으로 "다리"를 만들어 빈 공간을 메우는 방법도 있으나, 패널이 `<li>` 폭이 아니라 `.header` 전체 폭으로 펼쳐지므로 다리도 전체 폭을 덮어야 해서 더 복잡하고 깨지기 쉽다. `mouseleave`를 `.header`로 옮기는 쪽이 더 단순하고 근본적이다(부작용: 다른 GNB 항목으로 바로 이동하지 않고 로그인/검색/후원하기 버튼 위에 머물러도 메뉴가 곧바로 닫히지는 않지만, 헤더+패널 영역을 완전히 벗어나면 정상적으로 닫힌다 — 일반적인 메가메뉴 UX와 동일).

### 16. 서브페이지 5개(`/about` `/programs` `/story` `/news` `/donate`) 추가 — Phase 1 범위(메인 페이지만) 밖으로의 명시적 사용자 확장 (Step 0-8 이후 추가 작업)

- **무엇을**: PROJECT_SPEC §1.4/§15는 Phase 1 범위를 메인 페이지 하나로 한정하지만, 사용자 요청으로 실제 서비스 수준의 상세 레이아웃을 갖춘 서브페이지 5개를 추가했다. 나머지 메뉴/푸터 링크(약 35개)는 여전히 `/coming-soon` 스텁으로 남겨뒀다.
- **왜**: §2-9("범위 밖 기능 구현 금지... 필요해 보이면 구현하지 말고 질문한다")의 취지는 Claude가 스스로 판단해 범위를 넓히는 것을 막기 위함이다. 이번에는 사용자가 직접 "서브페이지도 만들어 달라"고 명시적으로 요청했고, 만들 범위(핵심 페이지 몇 개)와 완성도(실제 서비스 수준)까지 직접 선택했다 — §10("모호하면 멈추고 묻는다")의 취지대로 두 질문 모두 사용자에게 먼저 확인받은 뒤 진행했다. 결제·로그인·관리자 CMS(§2-9가 명시적으로 금지하는 항목)는 이번에도 만들지 않았다.
- **대안**: 스펙 문구를 근거로 서브페이지 자체를 거부하는 방법도 있었으나, 사용자가 이 프로젝트의 소유자이자 스펙 작성자 본인이라 스펙의 정신(임의로 범위를 넓히지 않는다)을 지키면서도 명시적 지시는 반영하는 쪽을 택했다.
- **부수 변경**: 새 페이지에 실제로 연결되는 링크(예: `/coming-soon/about/intro` → `/about`)만 갱신하고 나머지는 그대로 뒀다. `sitemap.ts`에 5개 경로를 추가했다(§11 "실제 콘텐츠가 있는 페이지만 사이트맵에 넣는다" 원칙을 그대로 적용). Pagination 컴포넌트는 §8 컴포넌트 체크리스트가 "Phase 2로 미룸(구현 금지)"라고 명시해 목록형 페이지(`/story`, `/news`)에도 구현하지 않고 정적 목록으로만 구성했다.

### 15. `public/illustrations/`의 자체 제작 일러스트 — §2 절대 규칙 4번("이모지·일러스트 금지")의 명시적 사용자 예외 (Step 0-8 이후 추가 작업)

- **무엇을**: Step 0-8 완료 이후, 사용자가 회색 placeholder 대신 실제 사진(저작권·초상권 문제로 배제)이 아닌 벡터 일러스트를 직접 그려 넣어달라고 명시적으로 요청해, `public/illustrations/`에 DS 색상 기반 일러스트 13종을 추가하고 `home.ts`/`nav.ts`의 이미지 슬롯에 연결했다.
- **왜**: PROJECT_SPEC §2 절대 규칙 4번은 "이모지·일러스트 금지, 아이콘은 24×24 아웃라인만 사용"이라고 명시한다. 이 규칙은 원래 원본(굿네이버스) 사이트의 산만한 이모지·일러스트 남용을 배제하기 위한 것으로 보이지만, 이번 요청은 사용자가 대안(직접 사진 업로드 vs 일러스트)을 제시받은 상태에서 명확히 후자를 선택한 것이라 §10("모호하면 멈추고 묻는다")의 취지대로 사용자에게 직접 확인했고, 규칙을 유지할지 예외로 둘지 다시 한번 물어 "그대로 유지"를 명시적으로 확인받았다. 스펙 규칙보다 스펙을 소유한 사용자 본인의 명시적 지시가 우선한다고 판단했다.
- **대안**: 규칙을 엄격히 지켜 일러스트를 되돌리고 회색 placeholder나 24×24 아웃라인 아이콘만 쓰는 방법도 제시했으나, 사용자가 명시적으로 "그대로 유지"를 선택해 채택하지 않았다.

### 1. `--white`, `--overlay-modal` 확장 토큰 추가 (Step 0)

- **무엇을**: PROJECT_SPEC §5.4가 정의한 확장 토큰 표에 없는 두 토큰을 tokens.css에 추가함.
  - `--white: #ffffff`
  - `--overlay-modal: rgba(0, 0, 0, 0.5)`
- **왜**: `check-tokens.mjs` 규칙 5("hex 색상 리터럴이 tokens.css 밖에 있음")를 지키려면 `globals.css`의 `body { background: ... }`가 하드코딩 hex가 아닌 변수를 참조해야 합니다. DS §0은 "캔버스: 항상 흰 배경"이라고 서술만 하고 별도 색상 토큰명을 주지 않습니다. Modal도 DS §8-8에 `overlay: rgba(0,0,0,0.5)`가 명시돼 있지만 시맨틱 토큰명이 없습니다. §2-3(토큰 외 값 금지)을 지키는 쪽이 §5.4 표를 그대로 두는 것보다 더 제한적인 규칙이라 판단해 토큰을 추가하는 쪽을 선택했습니다.
- **대안**: 두 값을 각각 사용처 CSS에 `ds-exceptions.json`으로 등록해 예외 처리할 수도 있었지만, 여러 컴포넌트(Modal 오버레이는 Step 1, body 배경은 Step 0)에서 반복 사용될 값이라 토큰화가 유지보수에 더 안전하다고 판단했습니다.

### 2. 단체명 기본값 표기 — `{{ORG_NAME}}` 대신 `'{{TODO}}'` 사용 (Step 0)

- **무엇을**: PROJECT_SPEC §16 표의 "기본값" 열에는 `{{ORG_NAME}}`이라고 적혀 있지만, 실제 `site.config.ts` 구현에는 §13.1의 `Todo = '{{TODO}}'` 타입 값을 그대로 사용함.
- **왜**: §2-2(사실 주장은 `'{{TODO}}'`로 둔다)와 §13.1의 타입 정의가 코드 레벨의 구체적 규칙이고, `check-todo.mjs`도 `{{TODO` 문자열만 탐지하도록 스펙에 정의되어 있습니다(§14.1). §16의 `{{ORG_NAME}}`은 사람이 읽는 설명적 표기로 해석해, 우선순위상 더 구체적이고 자동 검증과 맞물리는 §2/§13.1 쪽을 따랐습니다.
- **대안**: 두 표기를 병기하는 방법도 있었으나 자동 검사 스크립트와의 일관성을 위해 하나만 선택했습니다.

### 3. `/dev/components` — "빌드에서 제외" 대신 "런타임 404 + noindex"로 구현 (Step 1)

- **무엇을**: PROJECT_SPEC §4가 `/dev/components`를 "noindex, 프로덕션 빌드에서 제외"라고 명시했지만, 실제로는 라우트 자체는 빌드 산출물에 포함시키고 `NODE_ENV === 'production'`일 때 컴포넌트 최상단에서 `notFound()`를 호출해 404로 응답하도록 구현했습니다. 별도로 `layout.tsx`에서 `robots: { index: false, follow: false }`를 지정해 noindex도 보장합니다.
- **왜**: Next.js 16(App Router)에는 "특정 라우트 하나만 프로덕션 빌드에서 물리적으로 제외"하는 표준 옵션이 없습니다. `next.config.ts`에서 커스텀 웹팩/번들 설정으로 라우트를 지우는 방법은 PROJECT_SPEC §3이 정한 기술 스택(§3은 커스텀 번들러 개입을 언급하지 않음) 밖의 접근이라 판단해 배제했습니다. `notFound()` + `noindex`는 실사용자·크롤러 입장에서는 완전히 동일한 결과(접근 불가, 색인되지 않음)를 만들면서도 스펙이 정한 도구 범위 안에서 구현 가능한 가장 보수적인 방법입니다.
- **대안**: `middleware.ts`로 `/dev/components` 요청을 프로덕션에서 차단하는 방법도 있었으나, 미들웨어 도입 자체가 §3에 없는 새 구성 요소를 추가하는 것이라 더 큰 변경으로 보고 채택하지 않았습니다.

### 4. Checkbox의 시각적 숨김(sr-only) 패턴에서 `margin: -1px` 대신 `clip-path: inset(50%)` 사용 (Step 1)

- **무엇을**: 네이티브 `<input type="checkbox">`를 시각적으로 숨기고 커스텀 원형 UI로 대체하는 표준 접근성 패턴(sr-only)을 구현하면서, 흔히 쓰이는 `clip: rect(0,0,0,0); margin:-1px;` 대신 `clip-path: inset(50%)`만 사용했습니다 (margin 없음).
- **왜**: `-1px`는 `check-tokens.mjs`가 강제하는 허용 spacing 값 목록에 없고, 이 값은 DS 원문에 근거한 값이 아니라 범용 접근성 관용구라서 `ds-exceptions.json`(§2-7: "DS 원문에 근거가 있는 값만 등록")에 올릴 수도 없습니다. `clip-path: inset(50%)`는 음수 margin 없이 동일한 시각적 숨김 효과를 내는 최신 대안이라 규칙을 우회하지 않고 해결했습니다. 같은 패턴을 `common/VisuallyHidden` 컴포넌트로도 만들어 재사용합니다.
- **대안**: 규칙을 어기지 않는 선에서 다른 대안은 없다고 판단했습니다 (예외 등록은 규정상 불가능).

### 5. Footer 하단 블록 순서를 PC/Mobile 동일하게 유지 (Step 2)

- **무엇을**: DS §8-12는 Mobile 전용 구조에서 "고객문의(전화) → 회사정보" 순서를 명시하지만, 구현은 PC/Mobile 모두 "법인 정보 → 고객센터" 순서로 통일했습니다.
- **왜**: 브레이크포인트마다 DOM/시각적 순서를 다르게 하려면 CSS `order`로 시각 순서만 바꾸거나 마크업을 breakpoint별로 분기해야 하는데, 전자는 스크린리더 낭독 순서와 화면 순서가 어긋나는 부작용이 있고 후자는 마크업 복잡도가 커집니다. 두 블록 다 사실 정보(`{{TODO}}`)뿐이라 순서가 바뀐다고 정보 접근성에 실질적 차이가 없다고 보고, 더 단순하고 일관된(=보수적인) 단일 순서를 선택했습니다.
- **대안**: Mobile에서만 `order`로 시각 순서를 바꾸는 방법도 있으나, 스크린리더 낭독 순서와 화면 표시 순서가 달라지는 것을 피하기 위해 채택하지 않았습니다.

### 6. 하단 고정 후원 CTA 바의 노출 기준을 <768px 대신 <1024px로 확장 (Step 2)

- **무엇을**: PROJECT_SPEC §12는 "Mobile 하단 CTA 바"라고만 표현하지만, 실제로는 <1024px(=Mobile+Tablet 헤더가 햄버거 구조를 쓰는 전 구간)에서 노출되도록 구현했습니다.
- **왜**: PC(≥1024)에 플로팅 CTA를 두지 않는 이유는 "sticky 헤더에 후원하기 버튼이 항상 보이기 때문"(§12)인데, Tablet(768–1023)은 §8 기본값에 따라 Mobile 헤더 구조를 그대로 쓰므로 헤더 안에 상시 노출되는 후원 버튼이 없습니다(모바일 메뉴 안에만 있음). §12의 전제(항상 보이는 후원 버튼이 있으므로 플로팅 바 불필요)가 Tablet에는 성립하지 않아, 그 전제가 성립하는 구간(≥1024)까지만 플로팅 바를 숨기는 쪽이 "후원 도관을 없애지 않는다"는 더 보수적인 선택이라고 판단했습니다.
- **대안**: 문구 그대로 768px 미만에서만 노출하고 Tablet은 후원 CTA 없이 두는 방법도 있었으나, 핵심 전환 경로(후원하기)가 한 구간에서 사라지는 것이 더 큰 리스크라고 보고 채택하지 않았습니다.

### 7. Footer SNS 아이콘 — `lucide-react`의 `Youtube`/`Instagram`이 더 이상 존재하지 않음 (Step 2)

- **무엇을**: PROJECT_SPEC §5.6은 SNS 아이콘으로 `lucide-react`의 `Youtube`, `Instagram`을 지정하지만, 실제 설치된 `lucide-react`(현재 최신 안정 버전)에는 이 두 아이콘이 없습니다. `node_modules/lucide-react`의 export 목록을 직접 확인한 결과 브랜드/로고 아이콘이 라이브러리에서 전부 제거되어 있었습니다 — `AGENTS.md`가 경고한 "학습 데이터와 다른 최신 버전"의 실제 사례입니다.
- **왜**: 두 가지 대안(➊ 예전 버전의 `lucide-react`로 다운그레이드, ➋ 실제 브랜드 로고 모양을 직접 SVG로 재현) 모두 문제가 있었습니다. ➊은 §3이 정한 "최신 안정 버전" 기조와 어긋나고 다른 아이콘·타입 정의와의 호환성 리스크를 새로 만듭니다. ➋는 상표(로고)를 직접 재현하는 것이라 §2-5(edm 브랜드 자산 등 타사 자산 사용 금지 원칙)의 취지에 비추어 보수적으로 피하는 것이 안전하다고 판단했습니다. 대신 DS §4/§5.6과 동일한 규칙(24×24 viewBox, stroke 2px, round cap/join, currentColor)을 지키는 일반적인 픽토그램(영상 재생 아이콘 → 유튜브 링크, 카메라 아이콘 → 인스타그램 링크)을 새로 그려 넣었습니다.
- **대안**: 아이콘 없이 텍스트 링크만 두는 방법도 있었으나, DS의 "48px 원형 아이콘 버튼" 시각 패턴을 그대로 유지하는 것이 전체 디자인 일관성에 더 부합한다고 보고 대체 아이콘을 그리는 쪽을 선택했습니다.

### 8. Hero 슬라이더를 `embla-carousel-react` 없이 직접 구현 (Step 3)

- **무엇을**: PROJECT_SPEC §3은 캐러셀 구현에 `embla-carousel-react`를 쓰도록 지정하지만, Hero 슬라이더(S2)는 `useState` + CSS `opacity` 전환만으로 직접 구현하고 embla를 사용하지 않았습니다.
- **왜**: embla-carousel-react의 기본 동작은 좌우 스크롤(슬라이드) 전환이고, §7 S2가 요구하는 "600ms 페이드" 크로스페이드는 공식 `embla-carousel-fade` 플러그인이 있어야 자연스럽게 구현됩니다. 이 플러그인은 §3 허용 목록에 없는 새 의존성입니다. Hero는(캠페인 캐러셀 S6과 달리) 스와이프 제스처 요구가 없어(§7 S2 어디에도 "스와이프"라는 말이 없음), embla가 제공하는 핵심 가치(드래그·스와이프)가 애초에 필요하지 않습니다. 그래서 새 의존성을 추가하는 대신 순수 React state + CSS transition으로 직접 구현했습니다. 캠페인 캐러셀(S6)은 스와이프가 명시적으로 요구되므로 그대로 `embla-carousel-react`를 사용합니다(Step 4).
- **대안**: `embla-carousel-fade`를 추가하고 그 이유를 여기에 적는 방법도 지침(§8 "새 의존성은 §3 목록 밖이면 이유를 기록")상 허용되지만, 의존성을 하나라도 줄이는 쪽이 더 보수적이라고 판단해 직접 구현을 선택했습니다.

### 10. CampaignCarousel — embla 초기 측정 레이스 조건 수정 (Step 5, 버그 수정)

- **무엇을**: `embla-carousel-react`가 마운트 직후 컨테이너/슬라이드 폭을 측정하는 시점이 이 섹션의 퍼센트 기반 `calc()` 레이아웃 및 셀프호스팅 가변 폰트의 `display:swap` 교체와 경쟁해, 최초 `scrollSnapList()`가 실제보다 적게(경우에 따라 1페이지로) 계산되는 문제를 발견해 고쳤습니다. `requestAnimationFrame` 1회 + `document.fonts.ready` 완료 시점에 각각 `emblaApi.reInit()`을 한 번 더 호출해 초기 페이지 수를 안정적으로 보정합니다.
- **왜**: 사용자가 실제로 마우스를 움직여 인디케이터 버튼을 누르기까지는 이 레이스 조건이 해소될 시간이 충분해 실사용 영향은 낮지만, 최초 렌더 직후 매우 빠르게 상호작용하는 경우(자동화 테스트 포함) 페이지 수가 실제보다 적게 보이거나 "다음" 버튼이 아무 동작도 하지 않는 것처럼 보일 수 있어 근본 원인을 고치는 쪽을 택했습니다.
- **대안**: 클릭할 때마다 매번 `reInit()`을 호출하는 방법도 있었으나, 정상적인 페이지 전환 동작 자체를 방해할 수 있어 마운트 시점에만 보정하도록 범위를 좁혔습니다.

### 9. `[hidden]` 복원 규칙을 globals.css에 추가 (Step 3, 버그 수정)

- **무엇을**: 스토리 탭(S3)의 비활성 패널에 `hidden` 속성만 적용했는데도 화면에 계속 보이는 실제 버그를 발견해, `globals.css`에 `[hidden] { display: none; }` 규칙을 추가해 고쳤습니다.
- **왜**: `.grid`(`display: grid`)처럼 저작자(author) 스타일이 있는 요소에 네이티브 `hidden` 속성을 함께 쓰면, 브라우저 기본(User-Agent) 스타일 `[hidden] { display: none }`이 저작자 스타일에 밀려 무시됩니다(출처 우선순위상 UA < 저작자). PROJECT_SPEC §7 S3은 "비활성 패널은 hidden 속성만" 적용하라고 명시하므로, 이 표준 동작을 복원하는 규칙을 추가하는 것이 스펙의 의도를 살리는 가장 직접적인 수정이라고 판단했습니다. 회귀 테스트(`tests/e2e/home-sections.spec.ts`)도 추가했습니다.
- **대안**: 탭 패널마다 `hidden` 대신 조건부 렌더링(`{active && <Panel/>}`)으로 바꾸는 방법도 있었으나, 그러면 "모든 탭 패널을 서버 렌더링해 크롤러가 전체를 읽게 한다"는 §7 S3 요구를 못 지키게 되어 채택하지 않았습니다.

### 11. WebPage JSON-LD의 `name`에 전체 `<title>` 대신 `siteConfig.tagline`만 사용 (Step 6)

- **무엇을**: `<title>`은 `{siteConfig.name} | {siteConfig.tagline}` 형식(§11)을 그대로 쓰지만, `lib/jsonld.ts`의 `webPageJsonLd()`에 넘기는 `title`(→ JSON-LD `name` 필드)은 `siteConfig.tagline` 하나만 사용하고 단체명(`siteConfig.name`)을 붙이지 않았다.
- **왜**: `siteConfig.name`이 아직 `'{{TODO}}'`라서, 전체 `<title>` 문자열을 그대로 JSON-LD `name`에 넣으면 `"{{TODO}} | 아동과 지역사회를..."`처럼 `{{TODO}}`가 **부분 문자열로 포함된 채** 구조화 데이터에 노출된다. `lib/jsonld.ts`의 `omitTodo()`는 필드 값이 정확히 `'{{TODO}}'`와 같을 때만 제외하도록 구현했는데(§11의 "값이 `'{{TODO}}'`인 필드는 출력에서 제외한다"는 문구를 그대로 따른 것), 이 필드처럼 TODO 문자열이 다른 텍스트와 합쳐진 값은 그 규칙으로 걸러지지 않는다. 실제로 프로덕션 빌드 HTML을 검사해 이 leak을 발견했다. `<title>`(화면에 보이는 텍스트)에 TODO가 보이는 것은 기존 결정(DEVIATIONS #2)대로 의도된 것이지만, 검색엔진·생성형 검색이 그대로 읽어가는 구조화 데이터에 플레이스홀더가 섞여 들어가는 것은 §11의 취지(플레이스홀더를 구조화 데이터로 내보내지 않는다)에 어긋난다고 보아, WebPage의 `name`은 이미 완성된 문구인 `tagline`만 쓰도록 좁혔다.
- **대안**: `omitTodo()`를 "정확히 일치" 대신 "부분 문자열 포함" 검사로 바꾸는 방법도 있었지만, 그러면 필드 전체가 사라져(예: 제목이 통째로 빠짐) 오히려 검색엔진에 더 빈약한 정보를 주게 된다. 단체명이 필요 없는 필드(WebPage 이름)는 TODO를 포함하지 않는 문구로 좁히고, 단체명 자체가 의미 있는 필드(Organization의 `name`)는 기존처럼 정확히 일치할 때만 제외하는 쪽이 더 보수적이라고 판단했다.

### 12. Hero 비활성 슬라이드의 CTA 링크에 `tabIndex={-1}` 추가 (Step 7, 버그 수정)

- **무엇을**: `HeroSlider`에서 비활성 슬라이드(`aria-hidden="true"`)의 CTA(`Button`/`<a>`)가 키보드 Tab 순서에는 그대로 남아 있던 실제 버그를 axe(`aria-hidden-focus`)로 발견해, 활성 슬라이드가 아닐 때 `tabIndex={-1}`을 주도록 고쳤다.
- **왜**: `aria-hidden="true"`인 요소 안에 포커스 가능한 요소가 남아 있으면 스크린리더 사용자에게는 안 보이는(숨겨진) 콘텐츠로 선언해 놓고, 키보드 사용자는 Tab으로 그 안에 들어갈 수 있는 모순이 생긴다(WCAG 4.1.2, axe `aria-hidden-focus` serious). Opacity 크로스페이드로 구현하다 보니 비활성 슬라이드의 DOM 자체는 항상 존재해서 이 문제가 생겼다.
- **대안**: 비활성 슬라이드를 아예 언마운트(조건부 렌더링)하는 방법도 있었으나, §11("초기 HTML에 모든 캐러셀 슬라이드의 텍스트가 존재해야 한다")를 지키려면 모든 슬라이드가 서버 렌더링에 남아 있어야 해서 채택하지 않았다. `tabIndex={-1}`만 토글하는 쪽이 최소 변경이다.

### 13. Dropdown 트리거의 기본 텍스트 색을 `--text-04`에서 `--text-03`으로 (Step 7, 버그 수정)

- **무엇을**: Footer의 "관련 사이트" `Dropdown`이 선택 전 기본 상태에서 `--text-04`(#999999, 흰 배경 대비 약 2.8:1)를 쓰고 있던 것을 axe(`color-contrast`)로 발견해 `--text-03`(#666666, 약 5.7:1)으로 올렸다.
- **왜**: 이 텍스트는 disabled나 placeholder가 아니라 사용자가 실제로 클릭하는 활성 컨트롤의 라벨이라 WCAG AA 4.5:1을 만족해야 한다. 같은 문제(#999999 대비 미달)를 Footer의 개인정보 안내 문구에서 이미 한 번 발견해 `--text-03`으로 고친 전례(코드 주석, Footer.tsx)가 있어 동일한 조치를 적용했다. `Input`의 `::placeholder`/`:disabled`, `Button`/`IconButton`의 `:disabled` 상태가 쓰는 `--text-04`는 WCAG가 placeholder·비활성 컨트롤을 대비 검사에서 제외하므로 그대로 두었다.
- **대안**: 없음 — 토큰 값 자체를 바꾸지 않고 이 컴포넌트의 이 상태에만 이미 존재하는 다른 텍스트 토큰(`--text-03`)으로 바꾸는 것이 가장 국소적인 수정이다.

### 14. FeaturedVideo "자세히 보기" 버튼에 대상이 드러나는 `aria-label` 추가 (Step 7, 버그 수정)

- **무엇을**: S8 대표 캠페인 영상의 "자세히 보기" 버튼이 Lighthouse SEO 감사(`link-text`)에 "설명적이지 않은 링크 텍스트"로 걸린 것을 발견해, `aria-label={`${title} 자세히 보기`}`를 추가했다.
- **왜**: PROJECT_SPEC §9가 "링크 문구가 반복되는 '자세히 보기'에는 대상이 드러나는 aria-label 또는 시각적 숨김 텍스트를 붙인다"고 명시적으로 요구하는데, Step 5 구현 시 이 버튼에는 적용하지 못했던 누락이다. 같은 문구를 쓰는 스토리 벤토의 "자세히 보기"는 카드 전체가 하나의 링크(제목까지 같은 접근성 이름에 포함)라 이미 충분히 설명적이라 별도 조치가 필요 없다.
- **대안**: 없음 — §9가 지정한 정확한 해결 방법(대상이 드러나는 aria-label)을 그대로 적용했다.

### 3. Next.js 16.3.5 — 학습 데이터와의 버전 차이 대응 방식 (Step 0)

- **무엇을**: `next dev` 최초 실행 시 자동 생성된 `AGENTS.md`/`CLAUDE.md`가 "이 버전은 학습 데이터와 다를 수 있으니 `node_modules/next/dist/docs/`를 먼저 읽으라"고 안내함. 매 Step마다 전체 문서를 정독하는 대신, 그 Step에서 실제로 사용하는 API(예: `next/font/local`, `generateMetadata`, `sitemap.ts`/`robots.ts` 파일 컨벤션)에 해당하는 문서만 그때그때 확인하는 방식으로 진행하기로 함.
- **왜**: 스펙 진행 속도와 정확성의 균형. Step 0에서 `next/font/local` 문서를 확인해 현재 구현(변수 폰트 + `weight` range + `variable`)이 최신 API와 일치함을 확인했습니다.
- **대안**: 전체 문서를 한 번에 정독하는 방법도 가능하나, 매우 방대해 실제로 쓰지 않는 API까지 검토하는 비효율이 있다고 판단했습니다. Step 2(메타데이터), Step 6(사이트맵/robots/JSON-LD) 진입 시 관련 문서를 다시 확인할 예정입니다.
